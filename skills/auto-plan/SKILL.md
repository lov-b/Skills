# Auto Plan — 任务/需求结构化规划

根据用户提出的任务或需求，分析项目上下文，判定任务规模，输出结构化的三段式开发计划，帮助 Agent 和用户对齐目标并按阶段推进。

## 触发条件

以下任一情况启用本 skill：

- 用户消息以 `/auto-plan` 开头
- 用户说「制定计划」「任务规划」「需求分析」「拆解任务」「规划一下」
- 用户显式选中或 @ 本 skill
- 用户描述一个任务/需求，并要求做拆解、分析或规划

## 工作流程

```
Auto Plan Progress:
- [ ] Step 1: 需求收集与澄清
- [ ] Step 2: 项目上下文分析
- [ ] Step 3: 任务规模判定
- [ ] Step 4: 输出三段式计划
- [ ] Step 5: 确认与调整
- [ ] Step 6: 文档保存与可选推送
```

---

### Step 1: 需求收集与澄清

1. 读取用户提供的任务/需求描述
2. 若信息不足以判断任务全貌，用 **AskQuestion** 弹框补齐关键信息：
   - 涉及哪些项目/模块？
   - 是否有明确的产品需求文档或设计稿？
   - 是否有截止时间或优先级要求？
   - 是否有依赖的外部系统或接口？
3. 将收集到的信息整理为结构化需求摘要

**AskQuestion 不可用时**：必须先提示「当前模型无法呼出 AskQuestion，需要纯文本确认」，再在对话中用文本列出待确认项，等待用户回复后再继续；禁止静默跳过确认。

---

### Step 2: 项目上下文分析

1. 识别用户当前工作区所在项目
2. 扫描项目结构，了解技术栈、模块划分、现有代码组织
3. 若任务涉及多个项目，逐一定位并分析
4. 总结项目现状中与本次任务相关的部分：
   - 已有哪些相关功能/代码
   - 当前架构能否支撑新需求
   - 是否需要引入新依赖或新模块

---

### Step 3: 任务规模判定

根据以下维度判断任务规模：

| 规模 | 判定标准 | 特征 |
|------|----------|------|
| **小任务** | 可一次性完成 | 单项目、单模块；如小 bug 修复、单接口调整、配置变更 |
| **中等任务** | 涉及多项目或多模块，但需求单一 | 跨项目联调、单一功能的全链路开发、涉及 2-3 个项目的改动 |
| **大任务** | 涉及多个需求、多个项目 | 多需求并行、跨多项目多模块的系统性改造、新功能体系搭建 |

在对话中明确输出判定结果和判定理由。

---

### Step 4: 输出三段式计划

按以下结构输出完整计划（使用 markdown 格式）：

#### 第一部分：需求全貌

必须包含以下内容：

```markdown
## 一、需求全貌

### 1.1 任务描述
[用清晰、完整的语言描述任务/需求的具体内容，将用户的抽象描述转化为明确的技术需求]

### 1.2 目标
[本次任务要达成的最终目标，可量化的用量化指标描述]

### 1.3 项目现状
[当前项目中与本任务相关的现有功能、代码、架构现状]

### 1.4 完成标准
[任务完成到什么程度算「做完」，明确边界]

### 1.5 任务规模
[小任务 / 中等任务 / 大任务] — [判定理由]
```

#### 第二部分：阶段拆解

将任务拆解为可执行的阶段，每个阶段独立可交付：

```markdown
## 二、阶段拆解

### 阶段 1：[阶段名称]
- **目标**：本阶段要完成什么
- **涉及项目/模块**：列出涉及的项目和模块
- **具体内容**：
  1. 子任务 1：详细描述
  2. 子任务 2：详细描述
- **完成标准**：本阶段交付什么、达到什么状态算完成
- **预估工作量**：[小 / 中 / 大]
- **前置依赖**：[无 / 依赖阶段 X]

### 阶段 2：[阶段名称]
...
```

拆解原则：
- **小任务**：1-2 个阶段，不过度拆解
- **中等任务**：3-5 个阶段，按功能模块或项目维度拆分
- **大任务**：5+ 个阶段，按需求维度先拆、每个需求内再按模块拆分
- 每个阶段的粒度应保证 Agent 能在一次对话中完成
- 阶段之间标明依赖关系和执行顺序

#### 第三部分：验收标准

```markdown
## 三、验收标准

### 各阶段验收

#### 阶段 1：[阶段名称]
- [ ] 验收项 1：具体可检验的标准
- [ ] 验收项 2：具体可检验的标准

#### 阶段 2：[阶段名称]
- [ ] 验收项 1
- [ ] 验收项 2
```

**大任务额外要求 — 测试用例**：

```markdown
### 测试用例（大任务必填）

#### 阶段 1 测试用例
| 编号 | 测试场景 | 输入/前置条件 | 预期结果 | 优先级 |
|------|----------|---------------|----------|--------|
| TC-1.1 | [场景描述] | [条件] | [预期] | P0/P1/P2 |

#### 阶段 2 测试用例
...
```

最终验收标准：

```markdown
### 最终验收标准
- [ ] 所有阶段验收通过
- [ ] [端到端功能验证项]
- [ ] [性能/安全/兼容性要求]
- [ ] [文档/配置/部署要求]
```

#### 第四部分：执行进度

在计划文档中维护一个进度看板，Agent 每完成一个阶段后更新状态，下次读取文档时直接从进度看板判断当前位置，无需重新检索全文。

```markdown
## 四、执行进度

> 最后更新：{YYYY-MM-DD HH:mm:ss}

| 阶段 | 状态 | 完成时间 | 备注 |
|------|------|----------|------|
| 阶段 1：[名称] | ⬜ 未开始 / 🔄 进行中 / ✅ 已完成 | — | — |
| 阶段 2：[名称] | ⬜ 未开始 | — | — |
| ... | ... | ... | ... |
| **整体进度** | **X / N 阶段已完成** | — | — |
```

进度状态定义：
- `⬜ 未开始`：尚未启动
- `🔄 进行中`：当前正在执行
- `✅ 已完成`：已通过该阶段验收标准
- `❌ 阻塞`：因依赖或问题无法继续，备注栏说明原因

---

### Step 5: 确认与调整

输出计划后，用 **AskQuestion** 让用户确认。

选项应包含：
- 「计划符合预期，保存文档并开始执行第一阶段」
- 「计划符合预期，不保存文档直接开始执行」
- 「需要调整某个阶段的拆解」
- 「需要补充或修改需求描述」
- 「仅保存计划文档，暂不执行」

**AskQuestion 不可用时**：必须先提示「当前模型无法呼出 AskQuestion，需要纯文本确认」，再在对话中用文本选项让用户确认；用户回复前不继续执行。

用户确认后：
- 选择含「保存」的选项 → 进入 Step 6 保存文档，再按需开始执行
- 选择「不保存直接执行」→ 跳过 Step 6，按阶段顺序开始开发（可结合 java-backend-pipeline 等其他 skill）
- 选择调整 → 根据反馈修改对应部分，重新展示调整后的计划

---

### Step 6: 文档保存与可选推送

当用户在 Step 5 选择了包含「保存」的选项时执行。

#### 保存路径解析

按优先级解析保存目录：

| 优先级 | 来源 | 行为 |
|--------|------|------|
| 1 | 用户在本轮对话中明确给出路径 | 使用该路径，直接写入 |
| 2 | 用户级配置 `config.json` 中的 `defaultSaveDir` | 使用该路径，直接写入 |
| 3 | 均未指定 | 使用系统「下载」文件夹，直接写入 |

**落库即执行**：按优先级解析出保存路径后直接写入文件，无需 AskQuestion 确认写盘，方便用户在 IDE 中查看 git diff。

**默认下载目录（跨平台，禁止写死绝对路径）**：

| 系统 | 解析方式 |
|------|----------|
| macOS / Linux | `$HOME/Downloads`（不存在则回退 `$HOME`） |
| Windows | `%USERPROFILE%\Downloads`（不存在则回退 `%USERPROFILE%`） |

#### 文件命名

```
plan-{slug}-{timestamp}.md
```

- `slug`：任务主题的中文或英文短名（可中英混合），连字符分隔，≤40 字符；优先选择中文用户一眼能理解的命名
- `timestamp`：`YYYYMMDD-HHmmss`（本地时区）

#### 可选 commit + push

文件写入完成后，若用户级 `config.json` 中 `docsGitRepo` 有效，弹 **AskQuestion** 仅确认 Git 操作（commit + push），不再确认写盘。

流程：
1. 确认保存文件位于 `docsGitRepo` 工作树内
2. `git add` + `git commit`（message 按规范）
3. `git push`（失败须报告原因，不回滚本地 commit）
4. 无有效 `docsGitRepo` 时不展示 Git 选项，直接完成

**commit message 规范**：

```
docs(plan): 新增任务计划文档 — {一句话主题}

新增任务计划文档：{文件名}
任务规模：{小/中/大}
阶段数：{N} 个阶段
{可选：关键阶段概要}
```

**AskQuestion 不可用时**：必须先提示「当前模型无法呼出 AskQuestion，需要纯文本确认」，再用文本选项确认保存路径；用户回复前不写入文件。

## 进度更新规则

当 Agent 在后续对话中按计划执行开发时，须遵循以下规则：

### 读取进度
1. 若计划文档已保存，Agent 开始执行前**必须先读取文档的「四、执行进度」表格**
2. 根据进度表格直接定位到当前应执行的阶段，**不必重新分析整个计划**
3. 若文档中无进度表格（如早期版本），按第一阶段开始

### 更新进度
1. 开始某阶段时：将该阶段状态更新为 `🔄 进行中`，更新「最后更新」时间
2. 完成某阶段时：将该阶段状态更新为 `✅ 已完成`，填写完成时间，更新整体进度计数
3. 阶段受阻时：将状态更新为 `❌ 阻塞`，在备注栏写明原因
4. **每次状态变更后立即更新文档**（若文档已保存到磁盘）

### 跨对话续接
- Agent 在新对话中收到「继续执行计划」类指令时，读取计划文档的进度表格即可续接
- 无需用户重复描述需求或已完成的部分
- 若计划文档未保存，Agent 须提示用户提供计划内容或重新生成

## 补充：风险与依赖识别

在第一部分或第二部分中，如识别到以下风险须主动标注：

- **技术风险**：当前架构不支持、需引入新技术栈、性能瓶颈
- **外部依赖**：依赖其他团队接口、第三方服务、审批流程
- **数据风险**：涉及数据迁移、格式变更、兼容性问题
- **时间风险**：工期紧张、依赖项交付时间不确定

风险标注格式：`⚠️ 风险：[描述] → 建议：[应对措施]`

## 安装时配置（默认保存地址与文档仓）

**安装或首次同步到全局 skills 时**，Agent 须用 AskQuestion 询问默认文档保存目录：

| 选项 | 行为 |
|------|------|
| 使用系统下载文件夹 | 将默认目录记为跨平台 Downloads 解析结果 |
| 自定义目录 | 用户提供路径并写入配置 |
| 跳过（每次再问） | 不写配置；每次 Step 6 走确认流程 |

### 配置文件位置（强制：仓库外）

配置写入**用户级**路径，**禁止**写入 skills 仓库或技能源码目录：

| 系统 | 配置文件路径 |
|------|----------------|
| macOS / Linux | `$HOME/.config/auto-plan/config.json` |
| Windows | `%APPDATA%\auto-plan\config.json` |

目录不存在则创建。

用户指定或确认**存储目录**后：

1. 将 `defaultSaveDir` 与 `configuredAt` 写入用户级 `config.json`
2. **探测 git 仓库**（保存目录本身或其父目录）：

```bash
git -C "$SAVE_DIR" rev-parse --show-toplevel 2>/dev/null
```

3. 若发现仓库根路径：
   - 用 AskQuestion 确认：「是否将仓库 `<repo-root>` 配置到 config，便于计划落盘后 commit+push？」
   - 用户同意 → 写入 `"docsGitRepo": "<repo-root>"`
   - 用户拒绝 → `docsGitRepo` 置空
4. 未发现 git 仓库 → 不询问，`docsGitRepo` 留空

用户级 `config.json` 结构：

```json
{
  "defaultSaveDir": "<user-chosen-or-downloads-path>",
  "docsGitRepo": "",
  "configuredAt": "<ISO-8601>"
}
```

规则：
- 有用户级 `config.json` 且 `defaultSaveDir` 有效 → Step 6 优先提示该路径
- 有有效 `docsGitRepo` → Step 6 **必须**提供「commit + push 到配置仓库」选项
- 无配置或路径失效 → 回退 Downloads，AskQuestion 确认
- **不要**把绝对路径写进 `SKILL.md` 或提交进 Skills 仓库；只写入用户级 `config.json`

**AskQuestion 不可用时**：必须先提示「当前模型无法呼出 AskQuestion，需要纯文本确认」，再用文本选项确认；用户回复前不写入配置。

## 注意事项

- **不凭假设规划**：项目现状必须通过实际代码分析得出，不凭经验猜测
- **粒度适配**：小任务不过度拆解，大任务不遗漏
- **可执行性**：每个阶段的描述要足够具体，Agent 拿到就能开发
- **幂等输出**：相同输入产出相同计划，不引入随机性
- **AskQuestion 优先**：需用户决策时用弹框，不另开追问对话
- **AskQuestion 不可用时**：必须先提示「当前模型无法呼出 AskQuestion，需要纯文本确认」，再用文本选项让用户确认；用户回复前不继续执行
- **配置在仓库外**：本机 `defaultSaveDir` / `docsGitRepo` 只写用户级 `config.json`，禁止写进技能源码目录
- **安装探测 git**：指定保存目录后探测目录/父目录是否为 git 仓，经用户确认后写入用户级配置
- **落盘可推送**：有 `docsGitRepo` 时 Step 6 提供 commit+push；push 失败须回报原因且不回滚本地 commit
- **跨平台路径**：用 `$HOME` / `%USERPROFILE%` / `%APPDATA%` 解析，禁止写死绝对路径进 SKILL.md
- **进度即时更新**：Agent 每完成一个阶段须立即更新文档中的进度表格；跨对话续接时读取进度表格而非重新检索全文
