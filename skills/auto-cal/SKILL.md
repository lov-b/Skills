# Auto Cal

创建或维护一份长期使用的算法学习题录。文档按真实日期组织，重点保留题干、用户作答、官方参考答案、对比结论和可复用知识点。

需要初始化文档、补全结构或新增题目时，先读取 `references/cal-template.md`。

## 识别工作模式

根据用户当前请求选择模式：

1. **创建文档**：创建一份全新的算法学习文档。
2. **新增题目**：向已有文档加入一批题目。
3. **答案检查**：只检查指定题目的 `ans` 是否满足题意，不查询或泄露标准答案。
4. **参考答案**：查询 LeetCode 官方题解，填写 `ref ans`，对比 `ans` 并填写 `conclusion`。
5. **组合请求**：按用户明确要求组合执行；不要因用户要求检查答案，就自动进入参考答案模式。

如果目标文档或题目不明确，先从当前对话和工作区定位；仍存在多个合理目标时再询问用户。

## 通用规则

- 日期使用 `YYYY-MM-DD`，不得使用 `Day 1`、`Day 2` 等描述。
- 同一天新增的题目追加到已有日期章节，不重复创建日期章节。
- 保留用户已有内容，尤其不得覆盖、润色或清空 `ans`。
- 题目使用稳定锚点：`date-YYYY-MM-DD-题号`。
- 题目总览至少包含：日期、题目、难度、题型 / 考点、状态。
- 修改 Markdown 文件时使用最小范围补丁；不得重写整份文件。
- 新增题目和答案检查模式禁止泄露答案、关键解法提示或标准代码。
- 从网页取得的题干和题解应自行整理、转述，不大段复制原文。
- 题目、难度、Hot 100 归属和官方题解优先以 LeetCode 官方页面为准。
- 不能从官方来源确认的信息，不得标成“官方”。

## 定位文档

按以下优先级确定文档路径：

1. 用户明确给出的路径。
2. 当前对话已经在维护的算法文档。
3. 当前工作区的 `knowledge/cal.md`。

创建模式下，如果默认路径已存在，不得覆盖。应询问用户是继续维护原文档，还是指定新文件名。

若需要询问但 AskQuestion 不可用，必须先提示“当前模型无法呼出 AskQuestion，需要纯文本确认。”，再用编号选项询问；用户回复前不执行依赖该决策的写入或覆盖。

## 模式一：创建文档

1. 确认目标路径，检查文件是否已存在。
2. 读取 `references/cal-template.md`。
3. 创建总览、当天日期章节和“算法知识和注意点”章节。
4. 除非用户明确要求创建空文档，否则按“新增题目”的默认规则生成当天首批题目。
5. 只填写题干及题目元信息，保持 `ans`、`ref ans`、`conclusion` 为空。
6. 验证目录链接、日期锚点和题目锚点均可跳转。

## 模式二：新增题目

### 默认选题规则

用户没有覆盖时使用以下配置：

| 项目 | 默认值 |
|---|---|
| 来源 | LeetCode Hot 100 |
| 数量 | 4 道 |
| 难度 | 3 道 Medium、1 道 Hard |
| 多样性 | 尽量覆盖不同题型和核心考点 |
| 去重范围 | 最近 20 个自然日内做过的题目不得重复 |
| 更早历史 | 尽量避免重复，优先选择从未记录的题目 |
| 输出内容 | 完整题干，不给答案或解法提示 |

用户可以修改来源、数量、难度配比、语言、专题、日期和去重范围；本次请求中的明确设置覆盖默认值。

### 选题流程

1. 完整读取目标文档，提取已有题号、日期、难度、题型 / 考点和状态。
2. 按当前日期计算最近 20 个自然日，将其中出现过的题目作为硬排除项。
3. 从 LeetCode 官方 Hot 100 当前题单获取候选题，核对题号、标题和难度。
4. 按用户要求筛选难度，并为候选题标注主要题型和核心考点。
5. 先满足题型差异，再从合格候选中随机选择；不要只是固定取列表前几题。
6. 默认同一批题目不得全部依赖同一个核心考点。若存在足够候选，任意两题也应尽量避免仅有相同主考点。
7. 打开每道题的官方题目页，确认输入、输出、示例、约束和特殊规则。
8. 将题干完整转述到文档，包括：
   - 任务目标；
   - 输入与输出含义；
   - 重要定义和限制；
   - 足以理解题意的示例；
   - 数据范围、空值、重复值、下标或溢出等关键边界。
9. 只新增题干和空的 `ans`、`ref ans`、`conclusion` 标题，不写思路、提示、伪代码或答案。
10. 同步更新题目总览，初始状态记为“待完成”。

如果候选不足以同时满足来源、难度、数量、多样性和去重要求，应说明具体冲突。优先放宽“更早历史不重复”，不得静默突破最近 20 天硬排除；仍不足时等待用户调整规则。

### 题目状态

- `待完成`：`ans` 为空。
- `已作答`：`ans` 已有内容，但尚未完成参考答案和结论。
- `已完成`：`ref ans` 与 `conclusion` 均已完成。
- 每次修改后，根据正文实际内容刷新总览状态，不依赖旧状态文本。

## 模式三：答案检查

答案检查是受限评审，不查询 LeetCode 标准答案，也不填写 `ref ans` 或 `conclusion`。

1. 读取指定题目的完整题干和 `ans`。
2. 只根据题意与用户当前方案检查：
   - 是否覆盖题目要求；
   - 推理链路和关键不变量是否成立；
   - 数据结构或语言语义是否使用正确；
   - 时间、空间复杂度是否满足约束；
   - 边界、空输入、重复值、越界、溢出等是否遗漏；
   - 方案能否真正得到题目要求的返回值。
3. 结果只分为：
   - `可行`；
   - `方向可行但不完整`；
   - `不可行`。
4. 明确指出错误发生的位置、触发条件和需要注意的点，但不得给出正确算法、关键修正代码或标准答案。
5. 默认只在对话中返回评审结果，不修改文档。只有用户明确要求记录评审时才写入。
6. 若 `ans` 信息不足以判断，应指出缺失信息，不自行补全成正确方案。

## 模式四：参考答案

用户明确要求“标准答案”“官方题解”“ref ans”或等价内容时才进入此模式。

1. 定位指定题目，读取题干和用户 `ans`，保留原文。
2. 打开 LeetCode 官方题解；核对题目版本、方法适用条件和复杂度。
3. 如果官方题解无法访问或无法确认：
   - 明确说明无法核实官方来源；
   - 不使用社区答案冒充官方答案；
   - 请求用户提供官方题解链接或内容，或同意改为非官方参考解。
4. 在 `#### ref ans` 下写入：
   - 官方核心思路的独立转述；
   - 清晰的执行步骤；
   - 可运行实现；
   - 时间复杂度和空间复杂度。
5. 代码语言优先使用用户指定语言；否则沿用该文档或 `ans` 的语言；仍无法判断时默认 Java。
6. 参考官方方法独立编写解释和代码，不大段复制官方原文或代码。
7. 在 `#### conclusion` 下对比 `ans` 与 `ref ans`：
   - 用户方案正确的部分；
   - 与参考解的关键差异；
   - 用户方案存在的问题及其触发场景；
   - 本题需要记住的边界、语言语义或复杂度注意点。
8. 将总览状态更新为“已完成”。
9. 从 `conclusion` 中提炼可跨题复用的知识：
   - 仅沉淀通用规律、常见错误、判断方法和语言注意点；
   - 不把只适用于本题的答案细节机械复制过去；
   - 合并同义知识点，保留来源题目和记录日期；
   - 写入“算法知识和注意点”章节。

## 兼容已有文档

维护已有题录时：

- 缺少总览列时，可在不丢失数据的前提下补充“题型 / 考点”和“状态”。
- 缺少 `ref ans`、`conclusion` 或知识点章节时，只补缺失结构。
- 已存在的自定义标题和说明尽量保留。
- 已有题目没有稳定锚点时可补充，但不得改变可用的旧锚点。
- 不因格式升级重新生成或覆盖题干、`ans` 和历史结论。

## 完成前检查

- 目标文档路径正确，未覆盖其他文件。
- 所有日期都使用真实日期。
- 总览链接能够跳转，锚点无重复。
- 数量、难度配比、题源和用户自定义条件均满足。
- 最近 20 天没有重复题目；如有例外，已获得用户明确同意。
- 新增题目包含理解和作答所需的重要条件。
- 新增题目未出现答案、解法提示或暗示性小标题。
- 答案检查模式没有查询或泄露标准答案。
- 参考答案模式已写入 `ref ans`、`conclusion`，并更新状态和通用知识点。
- 用户原有 `ans` 和其他内容保持不变。
