# Optimize 结构化优化

按固定流程推进优化，避免跳过分析或无法衡量效果。**分步推进、实施前确认**：先分析与方案（可跨多轮对话），经用户确认改动方案与 diff 后再实施；流程阶段一致，复杂优化不必单次对话内完成。

## 分步推进原则

- **禁止**在未获用户确认前，跳过分析直接改代码，或在单次回复中擅自完成「分析 + 实施 + 验证 + 总结」
- **不强制轮次**：简单优化可一轮完成 Phase 0～4；**复杂优化允许多轮对话**与用户讨论方案、补充信息，不必赶在同一或固定次数对话内结束分析
- **实施前必确认**：进入 Phase 5 前，**必须**呈现修改方案 + **代码差异（diff）预览**，并用 **AskQuestion** 或等效对话内选项请用户选择是否执行
- **跨轮衔接**：每轮简要输出 checklist 进度；用户后续消息继续同一优化时，从上次进度接续，不重复已完成阶段（除非环境/代码已变）
- 信息补齐、方案讨论、环境刷新等：优先 **AskQuestion**，**避免**无上下文地另开纯追问对话
- 用户明确说「直接改」「按方案做」且方案已确认时，可进入 Phase 5，但仍须走现状分析

## 触发条件

以下任一情况立即启用本 skill：

- 用户消息以 `optimize：` 或 `optimize:` 开头
- 用户说「优化」「提升」「改进」「增强」「重构」，且指向已有功能而非新功能
- 用户说「性能优化」「检索优化」「安全加固」
- 用户显式选中或 @ 本 skill

若优化目标不清晰，先追问：优化哪个方面？当前效果如何？期望达到什么水平？

### 不适用场景

- 有明确 Bug → 使用 `/bugfix`
- 全新功能开发 → 使用 `/auto-plan` 或项目级开发 skill
- 纯需求分析不涉及代码改动 → 使用 `/auto-plan`

## 工作流程

复制以下 checklist 跟踪进度，每完成一步打勾：

```
Optimize Progress:
- [ ] Phase 0: 上下文收集
- [ ] Phase 1: 现状分析
- [ ] Phase 2: 目标定义
- [ ] Phase 3: 方案设计
- [ ] Phase 4: 方案确认（关口）
- [ ] Phase 5: 实施优化
- [ ] Phase 6: 环境刷新
- [ ] Phase 7: 效果验证
- [ ] Phase 8: 优化总结
- [ ] Phase 9: 总结归档
```

---

### Phase 0: 上下文收集

在开始分析前，收集必要的上下文信息：

1. **历史对话查阅**：检索 agent-transcripts，是否曾讨论过相同优化方向
2. **相关文档查阅**：查看项目中是否有优化方向梳理文档或技术总结
3. **当前代码状态**：阅读待优化模块的现有实现

**输出**：是否有历史讨论；相关文档要点；当前实现概述。

---

### Phase 1: 现状分析

分析当前实现的状态，建立优化基线：

1. **当前实现**：现有功能怎么做的？涉及哪些模块/文件/类？
2. **当前指标**（尽可能量化）：
   - 性能类：延迟（P50/P95）、吞吐量、资源消耗
   - 质量类：准确率、召回率、覆盖率、错误率
   - 工程类：测试覆盖率、代码复杂度
   - 用户体验类：操作步骤数、用户反馈
3. **已知不足**：当前实现有什么明确的问题或瓶颈？
4. **约束条件**：有哪些不能改动的依赖、接口或兼容性要求？

**关键原则**：
- 如果能获取定量指标，**必须在优化前记录基线**
- 如果无法量化，描述当前状态的具体不足
- 列出"当前不足"时要区分**事实**和**猜测**

**输出**：当前实现描述、基线指标、已知不足、约束条件。

---

### Phase 2: 目标定义

明确优化要达到的效果：

1. **优化目标**：具体要提升什么？（一个优化任务建议聚焦 1-2 个核心目标）
2. **验收标准**（尽可能量化）：
   - 示例："检索 Recall@10 从 X% 提升到 Y%"
   - 示例："问答首字延迟从 Xs 降低到 Ys"
   - 无法量化时："重构后通过所有现有测试，代码符合 XX 设计模式"
3. **非目标**：明确本次不做什么，避免范围蔓延
4. **回归底线**：优化后哪些现有功能绝对不能退化？

**输出**：优化目标、量化验收标准、非目标、回归底线。

---

### Phase 3: 方案设计

设计具体的优化方案：

1. **方案列举**：列出 1-3 个可行方案，每个方案说明核心思路、改动范围、预估效果、潜在风险
2. **方案对比**：

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 实现复杂度 | | |
| 预期效果 | | |
| 风险 | | |
| 侵入性 | | |
| 可回滚性 | | |

3. **推荐方案**：选定并说明理由
4. **改动清单**：列出具体要修改/新增的文件和改动意图
5. **测试计划**：优化后怎么验证效果？怎么确保无回归？

**输出**：方案对比表、推荐方案、改动清单、测试计划。

---

### 优化确认关口（Phase 5 前，必填）

**无论** Phase 0～3 历经几轮对话，进入 Phase 5 前**必须**完成本关口：

1. **输出**：优化目标摘要、选定方案、**受影响文件与 diff 预览**（或新建文件全文预览）
2. **AskQuestion** 请用户选择：

| 选项 | 行为 |
|---|---|
| 确认，按方案实施 | 进入 Phase 5 |
| 调整方案后再看 diff | 回到 Phase 3，更新后重新本关口 |
| 拆分为多步实施 | 将方案拆为子步骤，逐步确认和验证 |
| 暂不实施 | 输出分析记录，本次不改代码 |
| 取消 | 结束流程 |

规则：

- `prompt` 须含：优化目标一句话、方案要点、**diff 摘要**
- **禁止**未过本关口直接写代码（用户已明确「按上述 diff 改」且本关口已展示 diff 除外）
- 复杂优化在关口前可有多轮方案讨论；**关口与 diff 展示不可省略**
- 用户确认后，可在**下一轮对话**继续 Phase 5～8，checklist 进度保持

**输出**：用户选择；已确认的 diff / 方案。

---

### Phase 5: 实施优化

按确认的方案修改代码：

1. 按改动清单逐项实施
2. 遵循项目现有规范与工具类，不重复造轮子
3. 大型改动按模块分步提交，每步可独立验证
4. 新增代码需补充必要的测试
5. 修改现有逻辑时保持向后兼容（除非确认关口明确允许 breaking change）

**与 /bugfix 的区别**：
- /bugfix 强调"最小修复，不改无关代码"
- /optimize 允许为了优化目标而重构、新增、替换方案，但需在确认关口明确范围

**输出**：改动文件列表 + 每项改动的一句话说明。

---

### Phase 6: 环境刷新

代码或配置变更后，若运行环境需要更新才能验证，由 Agent **主动执行刷新**，并在对话中告知用户。

1. **判断是否需要刷新**（按改动类型）：
   - 后端代码 / Dockerfile → 重建并重启相关容器
   - 前端代码 / 依赖 → 重新 build 或重启 dev server
   - 依赖变更 → 重新安装依赖并重启服务
   - 仅文档 / 注释 / 纯测试改动 → 通常无需刷新
2. **执行刷新**：优先使用项目已有脚本或 `docker compose build/up`；只刷新受影响的服务
3. **确认就绪**：等待 healthcheck 通过或关键服务可访问后再进入验证
4. **对话告知**（必填）：说明刷新了哪些服务、执行了什么命令、当前状态

若刷新可能影响数据或需停机，优先用 **AskQuestion** 确认后再执行。

**输出**：是否刷新、执行的命令、各服务当前状态。

---

### Phase 7: 效果验证

**与 /bugfix 的核心区别：/bugfix 验证"Bug 是否消失"，/optimize 验证"指标是否提升"。**

1. **效果验证**：对比优化前后的指标（Phase 1 基线 vs 当前值）

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| （根据具体优化填写） | | | |

2. **回归验证**：运行现有测试，确保未引入退化
3. **边界验证**：异常输入、并发、大数据量等边界场景（如适用）
4. **若效果不达标**：
   - 分析原因（方案问题？实现问题？指标选择问题？）
   - 决定是否调整方案（回到 Phase 3）或接受当前效果
5. 若验证失败或引入新问题，回到 Phase 3 或 Phase 5，更新 checklist

**输出**：效果对比表、回归测试结果、是否达标、不达标时的分析。

---

### Phase 8: 优化总结

验证通过后，在对话末尾输出以下总结（必填）：

```markdown
## 优化总结

### 优化目标
[一句话描述优化了什么]

### 优化前现状
[当前实现的关键问题和基线指标]

### 历史分析衔接（如有）
[上次对话中的分析摘要；本次继承、验证或修正了哪些判断；无历史则写「无」]

### 优化方案
[做了什么改动，为什么这样做]

### 优化效果

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| | | | |

### 已知限制
[本次未覆盖的部分，后续可继续改进的方向]

### 当前状况
[已优化 / 部分优化 / 需后续跟进；列出验证结果]

### Git Commit Subject
```
<type>(<scope>): <中文描述>（必要的类名/接口名等可保持英文）
```
```

**Commit Subject 规范**：
- 使用 conventional commits：`perf`（性能）、`refactor`（重构）、`feat`（功能增强）、`test`（测试）、`style`（UI/UX）
- `scope` 填主要影响模块
- `<type>(<scope>):` 保持英文，冒号后描述用**中文**
- 每条 50 字以内
- 示例：
  - `perf(retrieval): 检索多路并行化，降低问答延迟`
  - `refactor(knowledge): 重构知识文档切片逻辑，按方法边界切分`

### Git 提交与推送（用户要求时）

修复总结完成后，若用户要求将优化提交到 Git：

1. **本地 commit** 按 Phase 8 给出的 subject 执行（用户确认后）
2. **远程 push** 仅在用户要求且远程可联通时执行
3. **远程不可联通**：**跳过 push**，**不回滚**本地 commit；说明「本地已 commit，远程 push 失败：\<原因\>」
4. push 失败**不影响**「优化已完成」结论

---

### Phase 9: 总结归档（AskQuestion）

Phase 8 对话总结输出后，**直接将总结写入默认路径**（落库即执行，无需确认写盘），方便用户在 IDE 中查看 git diff。写入后若用户要求 Git 提交，再用 AskQuestion 确认 Git 操作。

**默认路径与命名**：

- 目录：`<项目根>/docs/optimize/`（不存在则创建）
- 文件名：`optimize-{YYYYMMDD-HHmmss}-{title}.md`
- `title`：由优化目标一句话生成 slug（中文或英文，可中英混合），连字符分隔，去特殊字符，≤40 字符

**归档文件须包含以下章节**（从 Phase 8 总结扩展撰写）：

```markdown
# Optimize: {title}

> 归档时间：{timestamp}

## 优化目标
## 优化前现状
## 方案选择与理由
## 实施改动
## 效果对比
## 已知限制与后续方向
## 如何避免类似性能/质量退化
```

规则：

- **「如何避免类似退化」必填**（监控建议、测试补强、基线守护等）
- 用户选「自定义保存路径」时，在同会话内获取路径
- 用户确认保存后再写入；写入成功后在对话中告知**完整文件路径**
- 用户选「不保存」则 Phase 9 结束

**输出**：是否归档、文件路径（或「未保存」）。

## 特殊场景处理

### 优化引入了新 Bug

- 停止优化流程，切换到 /bugfix 修复新 Bug
- 新 Bug 修复后，回到 /optimize 的 Phase 7 重新验证
- 或回滚优化改动，回到 Phase 3 重新设计方案

### 优化方案需要架构变动

- Phase 3 中明确标注"需架构变动"
- 确认关口特别提醒用户影响范围
- 建议拆分为多步：先做架构调整（独立提交），再做具体优化

### 无法量化效果

- 在 Phase 2 说明为什么无法量化
- Phase 7 使用代码审查、设计评审或功能对比替代指标对比
- 总结中说明效果验证方式和局限

### 多个优化点一起做

- 每个优化点独立走流程
- 如有依赖关系，在 Phase 2 明确顺序
- 避免在一个 Phase 5 中混合多个不相关改动

## AskQuestion 不可用时（强制提示）

凡本 skill 流程需要 AskQuestion，若 Agent 无法呼起该工具：

1. **必须在对话中提示用户**：当前模型无法呼出 AskQuestion，需要纯文本确认
2. 随后用编号/选项文本列出待确认项，等待用户回复后再继续；**禁止**静默跳过确认

---

## 注意事项

- **AskQuestion 不可用时**：若无法呼起 AskQuestion，**必须在对话中提示**：当前模型无法呼出 AskQuestion，需要纯文本确认；再用编号选项做确认，禁止静默跳过
- **禁止跳步**：未做现状分析不进入方案设计；未过**优化确认关口**（展示 diff 并获确认）不进入 Phase 5；环境未就绪不进入验证；未做效果验证不输出「已优化」
- **允许多轮分析**：Phase 0～3 可跨多轮对话与用户讨论；**确认关口 + diff 不可省略**
- **跨轮接续**：继续同一优化时继承 checklist 与历史分析，不重复劳动
- **历史衔接**：Phase 0 有历史时，分析与总结须引用并对比上次结论
- **鼓励量化**：尽可能用数据说话，而不只是"感觉变好了"
- **允许分步实施**：大型优化可以拆成多步，每步独立确认和验证
- **效果不达标可接受**：如果效果不如预期但无退化，可以选择接受并记录
- **多优化场景**：每个优化点独立走完流程；全部完成后分别输出总结
- **需人工决策**：高风险或拿不准的优化方案，优先用 **AskQuestion** 对话内弹框请用户确认后再实施
- **Push 容错**：远程 Git 不可联通时跳过 push、保留本地 commit，必须在对话中通知用户及失败原因
- **总结可归档**：Phase 9 在 Phase 8 之后执行；默认保存至 `docs/optimize/`
