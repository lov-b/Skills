# Bugfix 结构化修复

按固定流程修复 Bug，避免跳过分析或过早下结论。**分步推进、修复前确认**：先分析与方案（可跨多轮对话），经用户确认修改方案与差异后再实施修复；流程阶段一致，复杂问题不必单次对话内完成。

## 分步推进原则

- **禁止**在未获用户确认前，跳过分析直接改代码，或在单次回复中擅自完成「分析 + 修复 + 回测 + 总结」
- **不强制轮次**：简单 Bug 可一轮完成 Phase 0～4；**复杂 Bug 允许多轮对话**与用户讨论方案、补充信息，不必赶在同一或固定次数对话内结束分析
- **修复前必确认**：进入 Phase 5 前，**必须**呈现修改方案 + **代码差异（diff）预览**，并用 **AskQuestion** 或等效对话内选项请用户选择是否执行修复
- **跨轮衔接**：每轮简要输出 checklist 进度；用户后续消息继续同一 Bug 时，从上次进度接续，不重复已完成阶段（除非环境/代码已变）
- 信息补齐、方案讨论、环境刷新等：优先 **AskQuestion**，**避免**无上下文地另开纯追问对话
- 用户明确说「直接修」「按方案改」且方案已确认时，可进入 Phase 5，但仍须走根因定位

## 触发条件

以下任一情况立即启用本 skill：

- 用户消息以 `bugfix：` 或 `bugfix:` 开头
- 用户说「解决bug」「修复bug」「fix bug」
- 用户显式选中或 @ 本 skill

若 Bug 描述不完整，先追问必要信息（现象、复现步骤、期望行为、相关模块/报错），再进入 Phase 1。优先使用 **AskQuestion** 以对话内选项弹框追问，在同一次请求中等待用户选择后继续流程；不要中断当前任务、另开一轮纯追问对话。

## 工作流程

复制以下 checklist 跟踪进度，每完成一步打勾：

```
Bugfix Progress:
- [ ] Phase 0: 历史对话查阅
- [ ] Phase 1: 拆解分析
- [ ] Phase 2: 问题研判
- [ ] Phase 3: 根因定位
- [ ] Phase 4: 方案制定
- [ ] Phase 5: 实施修复
- [ ] Phase 6: 环境刷新
- [ ] Phase 7: 回测验证
- [ ] Phase 8: 修复总结
- [ ] Phase 9: 总结归档
```

---

### Phase 0: 历史对话查阅

在开始分析当前 Bug 前，查阅是否曾在**历史对话**中讨论过同一问题：

1. **检索范围**：当前项目的 agent-transcripts（按报错信息、模块名、现象关键词搜索）
2. **重点识别**：上次是否**仅分析未修复**（已有拆解/根因/方案，但未实施 Phase 5+，或用户当时未做决断）
3. **提取并记录**：
   - 上次现象、根因判断、方案建议
   - 已排除的假设、待用户确认的事项
   - 若有 transcript ID，记下便于总结引用
4. **衔接方式**：将有效历史结论并入 Phase 1～4 输入；若上次根因已确认且环境未变，可直接验证后进入 Phase 4，不必从零调查
5. **无历史 / 无法读取**：注明「无可用历史上下文」，按常规流程继续

**输出**：是否有历史记录；上次结论摘要；本次需继承或重新验证的点。

---

### Phase 1: 拆解分析

将 Bug 拆成可验证的子问题：

1. **现象**：实际发生了什么？（报错信息、错误数据、UI 表现）
2. **复现**：最小复现步骤是什么？能否稳定复现？
3. **期望**：正确行为应该是什么？
4. **范围**：影响哪些模块、接口、用户场景？
5. **时间线**：何时引入？最近是否有相关变更？
6. **历史衔接**（Phase 0 有记录时）：与上次对话相比，现象是否一致？哪些结论可沿用？

**输出**：用条目列出上述要点；标注信息缺口，必要时先查代码/日志/配置补齐。

---

### Phase 2: 问题研判

基于拆解结果判断问题性质与优先级：

| 维度 | 需回答 |
|------|--------|
| 类型 | 逻辑错误 / 数据问题 / 配置问题 / 并发时序 / 依赖异常 / 其他 |
| 严重程度 | 阻塞 / 高 / 中 / 低 |
| 影响面 | 单点还是系统性？有无 workaround |
| 修复策略 | 热修复 / 根因修复 / 需架构调整 |

若存在多个子问题，按严重程度排序，明确本次修复范围。

**输出**：问题类型、优先级、修复范围（含暂不处理项及原因）。

---

### Phase 3: 根因定位

找到问题的真正原因，禁止在根因未确认时直接改代码。

1. 从现象出发，沿调用链、数据流向下追踪
2. 阅读相关代码、配置、日志，用运行时证据验证假设
3. 区分**根因**与**表象**；若暂时无法确认，列出待验证假设并逐项排除
4. 定位到具体文件/函数/配置项

**原则**：
- 先调查后修复，不凭猜测改代码
- 一次只验证一个假设
- 若涉及复杂调试，可参考 systematic-debugging 思路

**输出**：根因说明（含证据：代码位置、日志片段、复现结果）。

---

### Phase 4: 方案制定

针对根因设计修复方案：

1. 列出 1～2 个可行方案，说明利弊
2. 选定**最小正确修复**（优先根因修复，避免过度改动）
3. 评估副作用：是否影响其他功能？是否需要补测试？
4. 明确修改点清单（文件 + 改动意图）

**输出**：选定方案、修改清单、风险与回测计划。

---

### 修复确认关口（Phase 5 前，必填）

**无论** Phase 0～4 历经几轮对话，进入 Phase 5 前**必须**完成本关口：

1. **输出**：根因摘要、选定修改方案、**受影响文件与 diff 预览**（或新建文件全文预览）
2. **AskQuestion** 请用户选择是否执行修复：

| 选项 | 行为 |
|------|------|
| 确认，按 diff 修复 | 进入 Phase 5 |
| 调整方案后再看 diff | 回到 Phase 4，更新后重新本关口 |
| 暂不修复 | 输出分析记录（含历史衔接与 diff 预览），本次不改代码 |
| 取消 | 结束流程 |

规则：

- `prompt` 须含：根因一句话、方案要点、**diff 摘要**
- **禁止**未过本关口直接写代码（用户已明确「按上述 diff 修」且本关口已展示 diff 除外）
- 复杂 Bug 在关口前可有多轮方案讨论；**关口与 diff 展示不可省略**
- 用户确认后，可在**下一轮对话**继续 Phase 5～8，checklist 进度保持

**输出**：用户选择；已确认的 diff / 方案。

---

### Phase 5: 实施修复

按方案修改代码：

1. 只做与 Bug 相关的最小改动，不顺手重构无关代码
2. 遵循项目现有规范与工具类，不重复造轮子
3. 异常处理按项目规范：精准捕获、不吞异常、关键路径有日志
4. 若方案涉及多处子问题，逐项修复并记录

**输出**：改动文件列表 + 每项改动的一句话说明。

---

### Phase 6: 环境刷新

代码或配置变更后，若运行环境需要更新才能验证修复，由 Agent **主动执行刷新**，并在对话中告知用户。

1. **判断是否需要刷新**（按改动类型）：
   - 后端代码 / Dockerfile → 重建并重启相关容器（如 `api`、`worker`）
   - 前端代码 / 依赖 → 重新 build 或重启 dev server
   - 依赖变更（`requirements.txt`、`package.json` 等）→ 重新安装依赖并重启服务
   - 仅文档 / 注释 / 纯测试改动 → 通常无需刷新
2. **执行刷新**：优先使用项目已有脚本（如 `deploy.bat`、`scripts/deploy.ps1`）或 `docker compose build/up`；只刷新受影响的服务，避免不必要的全量重建。
3. **确认就绪**：等待 healthcheck 通过或关键服务可访问后再进入回测。
4. **对话告知**（必填）：说明刷新了哪些服务、执行了什么命令、当前状态（已就绪 / 失败及原因）。

若刷新可能影响数据或需停机，优先用 **AskQuestion** 对话内弹框确认后再执行。

**输出**：是否刷新、执行的命令、各服务当前状态。

---

### Phase 7: 回测验证

修复完成后必须验证，**无验证证据不得声称已修复**。

1. **原 Bug 复测**：按 Phase 1 的复现步骤验证问题已消失
2. **回归测试**：运行相关单元测试 / 集成测试 / 手动冒烟
3. **边界检查**：相邻功能、异常输入、并发场景（如适用）
4. 若验证失败，回到 Phase 3 或 Phase 4，更新 checklist

**输出**：执行的验证命令/步骤 + 结果（通过/失败）。

---

### Phase 8: 修复总结

所有问题验证通过后，在对话末尾输出以下总结（必填）：

```markdown
## Bug 修复总结

### Bug 内容
[一句话描述 Bug 现象；附关键报错或复现条件]

### 根本原因
[根因说明，指向具体代码/配置/数据问题；若承接历史分析，说明与上次结论的一致/修正]

### 历史分析衔接（如有）
[上次对话中的分析摘要；本次继承、验证或修正了哪些判断；无历史则写「无」]

### 解决方法
[做了什么改动，为什么能解决问题]

### 当前状况
[已修复 / 部分修复 / 需后续跟进；列出验证结果]

### Git Commit Subject
```
<type>(<scope>): <中文描述>（必要的类名/接口名等可保持英文）
```
```

**Commit Subject 规范**：
- 使用 conventional commits：`fix` 为主类型
- `scope` 填主要影响模块（如 `backend`、`frontend`、`api`）
- `<type>(<scope>):` 保持英文，冒号后描述用**中文**（必要的类名、接口名等可保持英文）
- 每条 50 字以内
- 示例：
  - `fix(backend): 修正知识检索中的空值检查`
  - `fix(api): 修复 UserProfileMoaService 返回值为 null 的问题`

### Git 提交与推送（用户要求时）

修复总结完成后，若用户要求将修复提交到 Git：

1. **本地 commit** 按 Phase 8 给出的 subject 执行（用户确认后）
2. **远程 push** 仅在用户要求且远程可联通时执行
3. **远程不可联通**（网络错误、timeout、无法解析 host 等）：
   - **跳过 push**，**不回滚**本地 commit
   - 在修复总结中说明：「本地已 commit，远程 push 失败：\<原因\>」
4. push 失败**不影响**「Bug 已修复」结论

---

### Phase 9: 总结归档（AskQuestion）

Phase 8 对话总结输出后，**直接将总结写入默认路径**（落库即执行，无需确认写盘），方便用户在 IDE 中查看 git diff。写入后若用户要求 Git 提交，再用 AskQuestion 确认 Git 操作。

**默认路径与命名**：

- 目录：`<项目根>/docs/bugfix/`（不存在则创建）
- 文件名：`bugfix-{YYYYMMDD-HHmmss}-{bugtitle}.md`
- `bugtitle`：由 Bug 一句话摘要生成 slug（中文或英文，可中英混合），连字符分隔，去特殊字符，≤40 字符；优先选择中文用户一眼能理解的命名

**归档文件须包含以下章节**（从 Phase 8 总结扩展撰写）：

```markdown
# Bugfix: {bugtitle}

> 归档时间：{timestamp}

## Bug 内容
## 根本原因
## 解决思路
## 修复方案
## 当前状况
## 如何避免此类 Bug
```

规则：

- **「如何避免此类 Bug」必填**（预防建议、测试补强、规范约束等）
- 用户选「自定义保存路径」时，在同会话内获取路径（用户一条消息或 AskQuestion 后续补充），**不**另开无上下文对话
- 用户确认保存后再写入；写入成功后在对话中告知**完整文件路径**
- 用户选「不保存」则 Phase 9 结束，不影响修复结论

**输出**：是否归档、文件路径（或「未保存」）。

---

## 注意事项

- **AskQuestion 不可用时**：若无法呼起 AskQuestion，**必须在对话中提示**：当前模型无法呼出 AskQuestion，需要纯文本确认；再用编号选项做确认，禁止静默跳过。
- **禁止跳步**：未做根因定位不进入实施；未过**修复确认关口**（展示 diff 并获确认）不进入 Phase 5；环境未就绪不进入回测；未做回测不输出「已修复」
- **允许多轮分析**：Phase 0～4 可跨多轮对话与用户讨论；**修复前关口 + diff 不可省略**
- **跨轮接续**：继续同一 Bug 时继承 checklist 与历史分析，不重复劳动
- **历史衔接**：Phase 0 有历史时，分析与总结须引用并对比上次结论
- **禁止过度修复**：只解决当前 Bug，不顺手改无关问题
- **多 Bug 场景**：每个 Bug 独立走完流程；全部完成后分别输出总结
- **无法复现**：在总结中说明，给出已排查范围和后续建议
- **需人工决策**：高风险或拿不准的修复方案，明确列出选项，优先用 **AskQuestion** 对话内弹框请用户确认后再实施；不要中断当前任务另开追问对话。
- **Push 容错**：远程 Git 不可联通时跳过 push、保留本地 commit，必须在对话中通知用户及失败原因
- **总结可归档**：Phase 9 在 Phase 8 之后执行；默认保存至 `docs/bugfix/`，用户可不保存或指定自定义路径
