# Auto Know — 八股知识管理

把网站和 AI 对话里的技术面试知识整理成可检索、可修订、可追溯的 Markdown 知识库。

核心原则：

- 先查已有知识，再决定新增、合并、修订、冲突保留或跳过；禁止机械 append。
- 问题标题保留真实面试问法，答案能够脱离原对话独立理解。
- 网站内容必须记录来源；技术结论优先由官方文档、规范或源码校验。
- 只做摘要、改写和少量必要引用，不批量搬运受版权保护的原文。
- 写入知识库后，再单独询问是否执行 Git commit / push。

## 触发条件

以下任一情况启用：

- 用户要求检索、整理、收录某个网站中的八股或面试题
- 用户要求从当前对话、历史对话或指定 transcript 提炼八股
- 用户要求补充、纠错、去重、分类或重构已有八股知识库
- 用户要求把若干技术问答归档成面试复习资料
- 用户显式选择 `auto-know`

仅要求即时回答一道题时正常回答，不自动落库；用户同时说“记录、收录、整理、归档、维护知识库”时才进入本流程。

## 工作模式

1. **网站检索模式**：按主题或指定网站检索候选问题与答案。
2. **对话提炼模式**：从用户问题和 Agent 回答中提取可复用的面试知识。
3. **知识库维护模式**：对已有条目去重、补全、纠错、拆分、合并或迁移分类。
4. **组合模式**：先从网站或对话提取，再与已有知识库交叉校验后落库。

## 工作流程

```text
Auto Know Progress:
- [ ] Phase 1: 确定范围与知识库位置
- [ ] Phase 2: 检索网站和/或对话
- [ ] Phase 3: 提取、归一化与技术校验
- [ ] Phase 4: 检索已有知识并形成归档决策
- [ ] Phase 5: 展示覆盖矩阵与补丁预览
- [ ] Phase 6: 写入并验证知识库
- [ ] Phase 7: 询问并执行可选 Git 操作
```

### Phase 1：确定范围与知识库位置

先识别：

- 来源：指定网站、开放网络、当前对话、历史对话、指定文件，或其组合
- 主题：如 Java 基础、集合、并发、JVM、Spring、MySQL、Redis、网络、操作系统、分布式
- 目标：新增题目、补全答案、纠错、专题整理、全库去重或目录重构
- 深度：速记版、标准面试回答、原理与追问版；未指定时使用“标准面试回答 + 常见追问”
- 时间范围：用户指定；未指定时优先使用当前可访问的最新资料

知识库根目录按以下优先级解析：

1. 用户本轮指定的目录或文件
2. 用户级配置 `defaultSaveDir`
3. 当前工作区中已存在的 `interview-knowledge/` 或 `knowledge/interview/`
4. 系统下载目录下的 `interview-knowledge/`

用户级配置位置：

- macOS / Linux：`$HOME/.config/auto-know/config.json`
- Windows：`%APPDATA%\auto-know\config.json`

机器相关绝对路径只写用户级配置，不写进 skill 仓库。存在多个可用知识库且选择会改变写入目标时才询问用户；否则按上述优先级继续。

### Phase 2：检索网站和/或对话

#### 网站检索

用户要求网站检索时必须实际浏览，不凭模型记忆冒充检索结果。

来源优先级：

1. 用户点名的网站或页面
2. 官方文档、语言/框架规范、JEP/RFC、项目源码与维护者文档
3. 成熟的面试知识库，例如 JavaGuide
4. 可信技术出版物或工程团队文档
5. 个人博客只作为补充线索，不作为争议结论的唯一证据

用户点名 JavaGuide 时：

- 优先检索 `javaguide.cn` 与 `interview.javaguide.cn`
- 按 Java 基础、集合、并发、JVM、Spring、数据库、缓存、计算机基础、分布式和系统设计等栏目定位
- JavaGuide 用于发现高频问题和已有解释；容易变化或存在版本差异的结论，再用官方资料校验
- 记录具体文章 URL，不只记录站点首页

每个候选至少记录：

- 原始问题或页面标题
- 来源 URL
- 页面/资料名称
- 检索或访问日期
- 来源类型：官方 / 规范 / 源码 / 面试题库 / 二手资料
- 能支持该结论的要点

检索不到正文、页面受限或只有搜索摘要时，明确标注证据限制，不补写成“已核实”。

#### 对话提炼

同时扫描用户消息和 Agent 回答，不只摘录用户问题。候选包括：

- 用户直接提出的概念、原理、对比、场景与排障问题
- 回答中可独立成立的原因、实现机制、适用边界、风险和常见误区
- 回答中出现的面试追问、方案比较和版本差异
- 后续对前面答案的纠正或补充

排除：

- 只对当前项目成立的业务规则
- 纯操作指令、闲聊和任务进度
- 没有足够上下文、无法独立表述的片段
- 仅为措辞重复、没有新增知识的信息

历史对话工具不可用时，只处理当前可见对话，并在结果中说明范围，不声称已扫描全部历史。

### Phase 3：提取、归一化与技术校验

将候选整理为独立问题单元：

1. **保留问题意图**：优先保留用户原始问法，只去除口头赘词并补全指代。
2. **统一别名**：记录同义问法，例如“HashMap 为什么线程不安全”和“HashMap 并发 put 有什么问题”。
3. **控制粒度**：
   - 能独立提问、独立回答的内容拆开。
   - 拆开会丢失必要上下文的内容放在同一题的追问中。
   - 不把多个无关问题压成一个宽泛专题。
4. **形成答案层次**：
   - 面试简答：先给出 30～90 秒可表达的直接答案。
   - 原理展开：解释关键机制、因果链与必要术语。
   - 常见追问：保留能继续深挖的相关问题。
   - 易错点与边界：注明版本、前提、例外和常见误解。
5. **技术校验**：
   - 区分事实、经验判断和推断。
   - 对版本敏感内容注明适用版本。
   - 来源冲突时不强行融合，列出差异和采用结论的依据。
   - AI 对话只能作为候选来源；关键技术结论应尽量由可信资料复核。

写入或修改知识条目前，读取
[references/knowledge-format.md](references/knowledge-format.md)，遵循其中的目录、条目和索引格式。

### Phase 4：检索已有知识并形成归档决策

写入前必须递归检索知识库中的 Markdown 文件和总索引：

1. 使用问题关键词、别名、核心类名/API、机制名和标签搜索候选条目。
2. 命中后阅读全文或完整条目，不能只看文件名或标题。
3. 比较问题意图、结论、适用版本、回答深度和来源。
4. 对每个候选作出一种决策：

| 决策 | 适用情况 | 动作 |
|------|----------|------|
| 新增 | 没有同义或上位条目 | 插入最相关专题，并更新索引 |
| 合并 | 已有条目正确但不完整 | 把新内容归位到简答、原理、追问、边界或来源 |
| 修订 | 已有结论过时或错误 | 更新正文，保留修订日期和依据 |
| 冲突保留 | 可靠来源存在版本或语境差异 | 并列说明差异，不静默覆盖 |
| 拆分/迁移 | 条目混杂多个问题或分类错误 | 保留稳定 ID，调整结构和索引 |
| 跳过 | 已有内容完整且本次没有新增价值 | 不修改文件，记录跳过原因 |

禁止：

- 仅因标题不同就重复新建
- 只在文件末尾追加，而不寻找语义上合适的位置
- 用较弱来源覆盖已有的官方结论
- 删除仍然有效的解释、来源或版本边界
- 为了版式统一而无意义地重写整个知识库

### Phase 5：展示覆盖矩阵与补丁预览

写盘前展示：

| 候选问题 | 来源 | 目标分类/文件 | 决策 | 变更摘要 |
|----------|------|---------------|------|----------|

同时列出：

- 新增、合并、修订、冲突保留、迁移和跳过的数量
- 将创建或修改的文件
- 每个文件的具体章节级补丁预览
- 无法验证或仍需用户决定的冲突

若冲突会实质改变技术结论或归档位置，先询问用户；其余情况展示预览后直接写入。

### Phase 6：写入并验证知识库

1. 只修改覆盖矩阵中确认需要变更的文件。
2. 新专题按参考格式创建；已有专题在语义最相关的位置更新。
3. 同步维护根索引和必要的分类索引，避免孤立文档。
4. 写入后检查：
   - 稳定 ID 是否唯一
   - 同义问题是否重复
   - 内部链接和目录索引是否有效
   - 新增/修订条目是否有来源或明确标注“来源：对话”
   - 版本敏感结论是否注明边界
   - Git diff 是否只包含本次知识库变更
5. 回显完整文件路径、处理结果和未解决事项。

### Phase 7：询问并执行可选 Git 操作

文件写入和验证完成后，检测 Git 仓库：

1. 优先读取用户级配置中的 `knowledgeGitRepo`
2. 配置无效或文件不在该仓库内时，从知识库目录向上执行 `git rev-parse --show-toplevel`
3. 未检测到仓库时，明确说明并结束，不询问无效的 push

检测到仓库后，单独询问：

1. `commit + push`：只暂存本轮修改的知识库文件，提交并推送当前分支
2. `仅 commit`：只创建本地提交
3. `仅落盘`：不执行 Git 操作

用户原话已经明确要求 commit 或 push 时，按动作粒度视为已授权；`push` 包含必要的本地 commit。未明确授权时不得自行提交或推送。

执行前：

- 展示完整 commit message
- 检查工作树，只暂存本轮修改文件
- 有无法安全隔离的重叠改动时停止 Git 操作，但保留已写入内容
- 不 force push，不自动 merge/rebase

推荐 commit message：

```text
docs(interview): 整理 {主题} 八股知识

新增/补充：{主要问题}
修订/去重：{主要调整}
来源：{网站、官方资料或对话}
```

push 失败时保留本地文件和已完成的 commit，明确报告网络、认证、上游或 non-fast-forward 等原因。

## AskQuestion 不可用时

需要用户选择归档冲突或 Git 操作，但当前环境无法呼起 AskQuestion 时：

1. 必须提示：“当前模型无法呼出 AskQuestion，需要纯文本确认。”
2. 随后列出编号选项，等待用户回复。
3. 用户回复前，不执行尚未授权的冲突覆盖、commit、push 或全局同步。
4. 文件落盘与 Git 操作是独立阶段；知识库已安全写入时，不因等待 Git 选择而回滚。

## 输出要求

最终结果至少包含：

- 检索或对话扫描范围
- 候选数与新增/合并/修订/冲突/跳过统计
- 修改后的绝对文件路径
- 主要问题标题与来源概览
- 校验结果和未解决限制
- Git commit / push 是否执行及结果

不要声称“已检索”“已去重”“已推送”，除非对应步骤实际完成。
