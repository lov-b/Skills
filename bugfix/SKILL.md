# Bugfix 结构化修复

按固定流程修复 Bug，避免跳过分析或过早下结论。每个阶段完成后简要输出结论，再进入下一阶段。

## 触发条件

以下任一情况立即启用本 skill：

- 用户消息以 `bugfix：` 或 `bugfix:` 开头
- 用户说「解决bug」「修复bug」「fix bug」
- 用户显式选中或 @ 本 skill

若 Bug 描述不完整，先追问必要信息（现象、复现步骤、期望行为、相关模块/报错），再进入 Phase 1。优先使用 **AskQuestion** 以对话内选项弹框追问，在同一次请求中等待用户选择后继续流程；不要中断当前任务、另开一轮纯追问对话。

---

## 工作流程

复制以下 checklist 跟踪进度，每完成一步打勾：

```
Bugfix Progress:
- [ ] Phase 1: 拆解分析
- [ ] Phase 2: 问题研判
- [ ] Phase 3: 根因定位
- [ ] Phase 4: 方案制定
- [ ] Phase 5: 实施修复
- [ ] Phase 6: 环境刷新
- [ ] Phase 7: 回测验证
- [ ] Phase 8: 修复总结
```

---

### Phase 1: 拆解分析

将 Bug 拆成可验证的子问题：

1. **现象**：实际发生了什么？（报错信息、错误数据、UI 表现）
2. **复现**：最小复现步骤是什么？能否稳定复现？
3. **期望**：正确行为应该是什么？
4. **范围**：影响哪些模块、接口、用户场景？
5. **时间线**：何时引入？最近是否有相关变更？

**输出**：用条目列出上述 5 点；标注信息缺口，必要时先查代码/日志/配置补齐。

---

### Phase 2: 问题研判

基于拆解结果判断问题性质与优先级：

| 维度 | 需回答 |
|------|--------|
| 类型 | 逻辑错误 / 数据问题 / 配置问题 / 并发时序 / 依赖异常 / 其他 |
| 严重程度 | 阻塞 / 高 / 中 / 低 |
| 影响面 | 单点还是系统性？有无 workaround |
| 修复策略 | 热修复 / 根因修复 / 需架构调整 |

若存在多个子问题，按严重程度排序，明确本次修复范围。

**输出**：问题类型、优先级、修复范围（含暂不处理项及原因）。

---

### Phase 3: 根因定位

找到问题的真正原因，禁止在根因未确认时直接改代码。

1. 从现象出发，沿调用链、数据流向下追踪
2. 阅读相关代码、配置、日志，用运行时证据验证假设
3. 区分**根因**与**表象**；若暂时无法确认，列出待验证假设并逐项排除
4. 定位到具体文件/函数/配置项

**原则**：
- 先调查后修复，不凭猜测改代码
- 一次只验证一个假设
- 若涉及复杂调试，可参考 systematic-debugging 思路

**输出**：根因说明（含证据：代码位置、日志片段、复现结果）。

---

### Phase 4: 方案制定

针对根因设计修复方案：

1. 列出 1～2 个可行方案，说明利弊
2. 选定**最小正确修复**（优先根因修复，避免过度改动）
3. 评估副作用：是否影响其他功能？是否需要补测试？
4. 明确修改点清单（文件 + 改动意图）

**输出**：选定方案、修改清单、风险与回测计划。

---

### Phase 5: 实施修复

按方案修改代码：

1. 只做与 Bug 相关的最小改动，不顺手重构无关代码
2. 遵循项目现有规范与工具类，不重复造轮子
3. 异常处理按项目规范：精准捕获、不吞异常、关键路径有日志
4. 若方案涉及多处子问题，逐项修复并记录

**输出**：改动文件列表 + 每项改动的一句话说明。

---

### Phase 6: 环境刷新

代码或配置变更后，若运行环境需要更新才能验证修复，由 Agent **主动执行刷新**，并在对话中告知用户。

1. **判断是否需要刷新**（按改动类型）：
   - 后端代码 / Dockerfile → 重建并重启相关容器（如 `api`、`worker`）
   - 前端代码 / 依赖 → 重新 build 或重启 dev server
   - 依赖变更（`requirements.txt`、`package.json` 等）→ 重新安装依赖并重启服务
   - 仅文档 / 注释 / 纯测试改动 → 通常无需刷新
2. **执行刷新**：优先使用项目已有脚本（如 `deploy.bat`、`scripts/deploy.ps1`）或 `docker compose build/up`；只刷新受影响的服务，避免不必要的全量重建。
3. **确认就绪**：等待 healthcheck 通过或关键服务可访问后再进入回测。
4. **对话告知**（必填）：说明刷新了哪些服务、执行了什么命令、当前状态（已就绪 / 失败及原因）。

若刷新可能影响数据或需停机，优先用 **AskQuestion** 对话内弹框确认后再执行。

**输出**：是否刷新、执行的命令、各服务当前状态。

---

### Phase 7: 回测验证

修复完成后必须验证，**无验证证据不得声称已修复**。

1. **原 Bug 复测**：按 Phase 1 的复现步骤验证问题已消失
2. **回归测试**：运行相关单元测试 / 集成测试 / 手动冒烟
3. **边界检查**：相邻功能、异常输入、并发场景（如适用）
4. 若验证失败，回到 Phase 3 或 Phase 4，更新 checklist

**输出**：执行的验证命令/步骤 + 结果（通过/失败）。

---

### Phase 8: 修复总结

所有问题验证通过后，在对话末尾输出以下总结（必填）：

```markdown
## Bug 修复总结

### Bug 内容
[一句话描述 Bug 现象；附关键报错或复现条件]

### 根本原因
[根因说明，指向具体代码/配置/数据问题]

### 解决方法
[做了什么改动，为什么能解决问题]

### 当前状况
[已修复 / 部分修复 / 需后续跟进；列出验证结果]

### Git Commit Subject
```
<type>(<scope>): <English description>
<type>(<scope>): <中文描述>
```
```

**Commit Subject 规范**：
- 使用 conventional commits：`fix` 为主类型
- `scope` 填主要影响模块（如 `backend`、`frontend`、`api`）
- **同时给出英文与中文两个版本**，`type` 与 `scope` 保持一致，仅描述部分分别撰写
- 每条 50 字以内
- 示例：
  - EN: `fix(backend): correct null check in knowledge retrieval`
  - CN: `fix(backend): 修正知识检索中的空值检查`

---

## 注意事项

- **禁止跳步**：未做根因定位不进入实施；环境未就绪不进入回测；未做回测不输出「已修复」
- **禁止过度修复**：只解决当前 Bug，不顺手改无关问题
- **多 Bug 场景**：每个 Bug 独立走完流程；全部完成后分别输出总结
- **无法复现**：在总结中说明，给出已排查范围和后续建议
- **需人工决策**：高风险或拿不准的修复方案，明确列出选项，优先用 **AskQuestion** 对话内弹框请用户确认后再实施；不要中断当前任务另开追问对话。
